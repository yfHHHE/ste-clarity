# 中文与双语示例

所有事实来自原文。说明与改写分开，不把待确认事项写成已知事实。

## 1. 保留建议和未定义的性能要求

**原文：** 当出现验证未能成功的情况时，接口应该尽快向调用方提供能够帮助其理解失败原因的相关信息。

**改写：** 验证失败时，接口应该尽快向调用方提供说明失败原因的信息。

**说明：** 保留“应该”和“尽快”。原文未给出响应时限或字段，不能补写为“必须在 200 ms 内返回 error_code”。

## 2. 许可、前提与禁止

**原文：** 仅当两个副本均处于健康状态时，才可以清空缓存，不得重新启动服务。

**改写：** 仅当两个副本都健康时，才可以清空缓存。不得重启服务。

**说明：** 健康条件没有变成执行命令；“可以”没有变成“必须”。

## 3. 不确定性和进度

**原文：** 目前核心功能基本完成，预计周五完成联调，暂未发现阻塞问题。

**改写：** 核心功能目前基本完成。预计周五完成联调。暂未发现阻塞问题。

**说明：** 不改成“开发已完成”“周五上线”或“没有阻塞问题”。

## 4. 缺失主体

**原文：** 审核完成后通知对方。

**改写：** 审核完成后通知对方。

**说明：** 未明确谁通知谁。需要可执行流程时，询问通知人和接收方；否则保留歧义，不猜测为某个部门通知客户。

## 5. 中文指令不等于翻译请求

**用户请求：** 请改写这段英文，让它更清楚：The API should quickly return useful error information.

**改写：** The API should return useful error information quickly.

**说明：** 英文原文保持英文。“quickly”和“useful”仍需定义，不能加入响应时限或字段。

## 6. 繁體與混合術語

**原文：** 若 request_id 為空，API 必須拒絕此請求，且不得建立 session。

**改寫：** 若 request_id 為空：

1. API 必須拒絕此請求。
2. API 不得建立 session。

**說明：** 保留繁體、識別字與兩項約束；兩項約束都在同一條件之下。

## 7. 按要求翻译并保留否定含义

**用户请求：** 翻译成中文：Operators are not required to restart the service after this update.

**译文：** 本次更新后，操作人员无需重启服务。

**说明：** “无需”不等于“不得”；不能译成禁止重启。

## 8. 应当不自动弱化

**原文：** 根据本规范，服务应当保留审计记录。

**改写：** 根据本规范，服务应当保留审计记录。

**说明：** 保留“应当”。没有提供规范的用词定义，不能改成“建议保留”或声称已经确认其强制程度。
